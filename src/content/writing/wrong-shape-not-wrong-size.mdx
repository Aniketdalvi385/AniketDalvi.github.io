<div class="abstract">
<p class="eyebrow">Abstract</p>

A local decision model fixed the problem that made me park GiTrust: routing accuracy went from 41% to 93% on the same 44 requests, on the same 8&nbsp;GB laptop, at a twentieth of the latency.

GiTrust is a command-line safety layer for Git: you say what you want in plain English, and a local model works out which operation you mean. In August 2026 I parked it on a negative result. The local 3B language model (qwen2.5:3b) routed only 41% of a 44-request test set correctly, took about 10&nbsp;s per request, and sent some destructive requests straight to destructive operations. A bigger model did not fit in 8&nbsp;GB. My conclusion then, written up in [When the LLM Is the Weak Link](/writing/when-the-llm-is-the-weak-link), was that the intelligence belongs in deterministic code around a small model, not in the model.

In October I came back with a different _kind_ of model. Kev-0.8B is an open re-creation of Jev, TypeSafe's "System One" decision model: it never writes text, it returns a calibrated probability for each option on a list it is given. Stock Kev routed 70%; a fine-tune I trained on a free Colab GPU, with \~1,500 synthetic requests over GiTrust's 36 operations, routed 41/44 (93%) at about 0.5&nbsp;s. Run through the whole tool, it never took a wrong action that changed the repository on 68 phrasings I wrote myself; on 338 written blind by three persona agents, v0.5.0 has one such misroute, and it stops before doing anything.

The August finding survives and gets sharper: the deterministic layers are still what make the tool safe. What was wrong was the corollary that no local model could do better. **Model type mattered more than size.**

</div>

## <span class="num">01</span>The problem: reading intent, locally, without ever acting on a guess

GiTrust turns a plain-English request into a safe Git operation, and the hard part was never the Git — it was knowing which operation the person meant.

The tool exists for the colleague who just ran `git reset --hard`, force-pushed over a teammate, or can't find work they were sure they committed. You type `push the login changes` or `undo my last commit but keep the files`. GiTrust works out the intent, shows a plan, and runs it through gated, snapshotted, reversible steps. Three commitments define it:

<ul>
	<li>
		<span class="b">→</span>
		<span>
			**Local only.** No diff, code or query leaves the machine, so the
			model runs on the laptop: an Apple M2 with 8&nbsp;GB of RAM.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**The model reads intent; it never runs or writes commands.** It
			picks an operation. Arguments, commit messages and destructive
			strategies come from the user or from deterministic code.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Safe by construction.** Anything that can lose work is spelled out
			before it runs, snapshotted before it executes, and backed up first
			if Git itself can't recover it.
		</span>
	</li>
</ul>

The request passes through five layers: context (which of 12 repo situations you are in), intent, a situation gate, file resolution, then validation and execution. Everything after intent is deterministic. So the whole product rests on one question asked of the model, in two forms:

<ul>
	<li>
		<span class="b">→</span>
		<span>
			**Problem A — routing.** Which of GiTrust's operations (36 by v0.4)
			does this request mean? A wrong answer on a destructive operation is
			the worst failure the tool can have.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Problem B — file scoping.** For "push the login changes", which of
			the changed files belong to _login_? This is fuzzy content
			judgement, and it decides what gets committed.
		</span>
	</li>
</ul>

Canonical phrasings were never the issue: an exact-phrase table handles `status` or `undo`. The issue is every phrasing nobody enumerated, which is most of what real people type.

## <span class="num">02</span>Why I parked it in August

I parked GiTrust because the local language model was the weakest component in it, and the one fix that might have helped — a bigger model — crashed the laptop.

The first acceptance runs showed the pattern: every operation worked for its one canonical phrasing and misrouted almost everything else. Widening the exact-phrase tables was the obvious patch, and I rejected it — it makes the user rigid and doesn't adapt to phrasings nobody listed. So I built a 44-request diagnostic set (canonical requests, unseen paraphrases, scope variants, safety-critical requests, out-of-scope ones) and measured the fallback with the exact-phrase path bypassed:

The accuracy was not the worst of it. **Neither engine was safe alone on destructive requests:** the LLM routed "throw away my changes" straight to `reset`, and the embeddings routed "undo the last three commits" to `squash`.

The model-swap study closed the remaining door. The classifier prompt needs a 2,048-token context; a 4B model at that context OOM-crashed the 8&nbsp;GB M2 and ran \~1.9× slower. Llama 3.2 3B emitted less reliable JSON, a downgrade for a JSON classifier. Three of those benchmark runs also produced convincing but false numbers before a real one — models not unloaded between runs, a hidden `<think>` block emptying the output, a context too small that silently truncated the prompt.

What shipped was a deterministic-first hybrid: exact phrases, then a margin-gated embedding router that abstained on anything destructive, then the LLM as a last resort, with every destructive outcome decided by a deterministic gate. It worked, but the model had been demoted to coarse classification, and Problem B (file scoping) stayed unsolved. My conclusion: **for local Git-intent routing on 8&nbsp;GB, a 3B language model is the wrong tool for the precision this domain needs.**

## <span class="num">03</span>The shift: a model that ranks instead of writes

Routing is choosing from a closed list, and a decision model does exactly that — so the question was never "how big a model" but "what kind".

My August study only compared generative models. [Jev](https://www.datacamp.com/blog/system-one-models-jev), launched by TypeSafe in September 2026, is a different kind: a "System One" model that returns a probability for each option in a schema instead of generating text. Jev is hosted, so it breaks GiTrust's local-only rule. [Kev](https://github.com/jaredpalmer/kev) is an open re-creation of the architecture [Archer Hume inferred for Jev](https://archerhume.com/posts/jevs-architecture-unmasked) from about 10,000 API calls, in four sizes from 0.8B to 27B.

How Kev-0.8B works, from its source:

<ol>
	<li>
		<span class="b"></span>
		<span>
			**Backbone:** Qwen3.5-0.8B, frozen, with a rank-16 LoRA adapter.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>
			**Input:** the state (here, the request plus one line of repo
			state), then each question with its options, then a `<decide>`
			token. Questions share the state but can't see each other.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>
			**Pointer head:** the hidden state at `<decide>` is a query, each
			option's `</opt>` hidden state a key; the option's score is their
			scaled dot product.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>
			**Output:** a softmax over the options, divided by a fitted
			temperature so the probabilities are calibrated. No text is
			generated, so there is nothing to parse.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>**Training:** cross-entropy on the correct option.</span>
	</li>
</ol>

That shape removes the August failure modes by construction:

I also asked whether an energy-based model would fit better. Energy-based _reasoning_ models such as Logical Intelligence's Kona score a candidate reasoning trace and refine it by optimisation; energy-based _reward_ models refine a reward model's scores for RLHF. Both search for or score open-ended outputs. Routing needs neither: the candidates are a short list I write, the normalisation is an exact sum over 36 options, and one pass is enough. A model that searches for a "solution" would reopen the problem v0.4 closed — the model producing the answer instead of choosing it.

The cost is memory. Kev-0.8B's server holds about 2.9&nbsp;GB (peak 3.1&nbsp;GB), more than its 1.5&nbsp;GB of weights, and it can't share 8&nbsp;GB with qwen (co-resident: \~30&nbsp;s per request and 16&nbsp;GB of swap). So Kev **replaces** the language model; it doesn't join it.

## <span class="num">04</span>What I did: measure, fine-tune, then fence it in

The work had three steps: measure stock Kev on the August test set, fine-tune it for GiTrust's 36 operations, and wire it in so it can only ever _narrow_ the choice, never make it.

**Step 1 — measure stock Kev on the same 44 requests.** Same labels, exact-phrase path bypassed. Stock Kev-0.8B routed 31/44 (70%), rejected 4/4 out-of-scope requests, got 4/5 of the safety bucket, and answered in a median 433&nbsp;ms. It routed both August disasters correctly ("throw away my changes" → clean-up, "undo the last three commits" → undo). But it was rarely confident: under the policy I planned, it would act on its own on only 8 of 44 requests and show a menu for the rest. Its argmax also flipped on 18/44 requests when the options were shuffled — though never on a confident one.

**Step 2 — fine-tune it.** Training on the laptop failed three times (the MPS backend ran out of memory moving weights, and system free memory hit 1%), so I moved training to a free Colab T4. Only synthetic phrasings are uploaded; inference stays local.

<ul>
	<li>
		<span class="b">→</span>
		<span>
			**Data:** 1,251 records in round 1, 1,481 in round 2 — routing
			phrasings with casing and politeness variants, six repo-state
			shapes, and mid-rebase/cherry-pick phrasings.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Hold-out discipline:** every topic, branch name and count used in
			the test set was banned from training slots; any training phrasing
			equal to a test request, or with content-word overlap ≥ 0.6, was
			dropped. The 44-request set was never uploaded.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Run:** LoRA delta from stock Kev, 2 epochs, \~100 minutes, with a
			permutation-consistency loss so the answer depends less on option
			order.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Calibration:** the fine-tune ships with raw logits and is
			over-confident. I fitted a temperature on the held-out dev split,
			never on the test set: T = 4.0 for round 2.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Round 2** added a 36th operation, _commit and push_, after the
			owner-written test set showed requests for it had nowhere to go. The
			result is published as
			[`AniketDalvi385/gitrust-kev-0.8b@v2`](https://huggingface.co/AniketDalvi385/gitrust-kev-0.8b).
		</span>
	</li>
</ul>

**Step 3 — fence it in.** Calibration can't see a _confident_ mistake, so every check I added can only turn "act" into "ask":

<ul>
	<li>
		<span class="b">→</span>
		<span>
			**Act only when confident:** p ≥ 0.5, and ≥ 0.6 for anything that
			discards or rewrites work. The first stock run showed why: "discard
			my local commits" went to clean-up at 0.53.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**The request's own words veto the model:** if Kev says plain
			_push_ but the words name a topic ("push the login changes"), the
			user gets a menu.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**A second opinion for destructive routes:** they are re-asked with
			the options in reverse order; a different answer becomes a menu.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Refuse only when sure:** "not a Git request" needs p ≥ 0.9; below
			that, a menu of Kev's top operations.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**The model never supplies arguments:** branch names, counts, files
			and quoted commit messages are captured from the words or asked for,
			and GiTrust never drafts a commit message.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Destructive outcomes still go through deterministic gates**, a
			snapshot and a backup, exactly as in August.
		</span>
	</li>
</ul>

Problem B uses the same model differently: GiTrust asks Kev one yes/no question per changed file ("is this part of _login_?") and bands the answer — confident yes pre-selected, confident no left out, the middle shown as "your call".

Stock Kev already beat both August engines; the fine-tune added 23 points without adding latency.

Model-level numbers flatter any classifier, so every release since v0.4 is also measured through the whole binary: each request runs as `gitrust --yes "<request>"` in a fresh repo, exact phrases and all checks included, and is scored right, asked (a menu, which `--yes` refuses), or wrong. A wrong action that _changes the repository_ is the number that matters.

The one remaining wrong route on the blind set — "save all my work with message 'add login page'" → _push only some changes_ — finds no topic in the words and stops with "nothing was done", exit 1. The blind set matters most. ## <span class="num">06</span>Testing it the way a user would

Once the model was good, the bugs that mattered were in my deterministic code — and they were found by driving the real binary, not by the unit tests that already passed.

For v0.4.1 I built a separate test repo, [GiTrust-test](https://github.com/Aniketdalvi385/GiTrust-test-repo). A pseudo-terminal drives the release binary through scripted tests, presses the keys a user would, and checks the exit code, the repository and the screen; each test runs in its own scratch home folder, bare remote and clone. Review agents then read every recorded screen against the product's conventions, and I re-ran the four flagship tests by hand.

The first full run (43 tests and the 450-request eval) found 20 problems, F1–F20. None lost data, but three were wrong actions or traps:

<ul>
	<li>
		<span class="b">→</span>
		<span>
			**F3:** "pull the latest from origin into this branch" matched an
			exact-phrase rule I had written for _sync_, and ran a merge of main.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**F19:** "merge develop into feature" ignored _develop_ and could
			run backwards.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**F7:** after a conflict pause, a snapshot stayed behind that
			`--recover` would later restore over the user's finished rebase.
		</span>
	</li>
</ul>

Fixing them for v0.5.0 turned up 11 more (F21–F31), and **two of those lost uncommitted work in v0.4.1**: a fast-forward used a git2 call whose default is a _forced_ checkout, wiping edits to files the update didn't touch; and hard-reset backups copied unstaged edits but skipped staged ones. The test suite was also writing snapshots into the real `~/.gitrust`.

That is the August lesson again from the other side — the deterministic layers carry the safety, so that is where the testing has to look.

## <span class="num">08</span>Limitations

This is a single-system case study on one laptop with small, mostly synthetic test sets, and several of its numbers carry caveats a reader should weigh.

<ul>
	<li>
		<span class="b">→</span>
		<span>
			**Calibration can't see a confident mistake.** Round 1 sent "push
			all api changes" to plain _push_ at 0.96; v0.4.1 sent a stash
			request to _restore stash_ at 0.91. Thresholds don't catch these;
			the words veto, the reversed re-ask and the gates do, and the next
			one may slip past all three.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Some of the 44-request gain was taught.** Round 2 trained the
			`push all {topic} changes` shape with other topics, so its fix on
			the August set is partly taught, not generalised. The blind set is
			the cleaner measure.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**The test sets were written by Claude.** The blind set never saw
			the training data, but the training templates were also written
			with Claude, so it is independent of the data, not of the model
			family that wrote it. Real users' phrasings remain the stronger
			test.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Problem B is only smoke-tested.** Sixteen one-line fixtures whose
			file names give the answer away. A realistic multi-feature diff is
			untested.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Small numbers.** 44, 68 and 338 requests; one fine-tune seed;
			differences of one or two requests are noise.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Order sensitivity remains.** 37–39 of 44 requests keep their
			answer under six shuffles of the options, not 44. GiTrust freezes
			the option order and re-asks destructive routes reversed.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**One machine, one person.** An Apple M2 with 8&nbsp;GB; latency and
			memory will differ elsewhere, and the owner-written set reflects one
			person's phrasing.
		</span>
	</li>
	<li>
		<span class="b">→</span>
		<span>
			**Memory is still the price.** Kev holds \~2.9&nbsp;GB while serving,
			and the first request after it has been idle waits \~25&nbsp;s for it
			to start.
		</span>
	</li>
</ul>

## <span class="num">09</span>Lessons

The lesson I would carry to the next tool is to match the model's _shape_ to the decision before reaching for a bigger one.

<ol>
	<li>
		<span class="b"></span>
		<span>
			**Model type beat model size.** A 0.8B model that ranks a closed
			list beat a 3B model that writes text, by 52 points, on the same
			hardware. My August model-swap study compared sizes of the wrong
			kind; the answer was a different kind.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>
			**Keep the intelligence in the deterministic layers.** Captures,
			gates, snapshots and backups made the tool safe with a weak model,
			and they still carry the safety with a good one. The model only
			narrows the choice.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>
			**Calibration is an interface.** A probability you can threshold
			lets code decide when to act, ask or refuse. Without it, every model
			output is either trusted or ignored.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>
			**Fence in what calibration can't see.** Add checks that can only
			turn "act" into "ask": the request's own words, a reordered second
			opinion, a higher bar for anything destructive.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>
			**Measure the whole system, from outside.** Model-level accuracy hid
			nothing dangerous here, but the real binary did: a forced checkout,
			a backup that skipped staged files, an exact-phrase rule that ran
			the wrong merge. All were found by driving the release binary in a
			terminal.
		</span>
	</li>
	<li>
		<span class="b"></span>
		<span>
			**Write the negative result down.** The August paper is why the
			October comparison was like for like: same test set, same labels,
			same harness, with the exact-phrase path bypassed the same way.
		</span>
	</li>
</ol>
